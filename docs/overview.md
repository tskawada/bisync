# bisync — Architecture Overview

bisync is a bidirectional file synchronisation daemon for two Linux hosts. It watches local filesystem changes with fanotify, records them in a SQLite changelog, and propagates them to the peer using rsync over SSH. A gRPC control plane handles changelog exchange, delete and rename commands, and health checks.

The two nodes are strict peers. Neither has a special role; each runs an identical daemon with a config file that names the other as `peer`. There is no central coordinator.

## Component overview

```
┌─────────────────────────────────────────────┐
│                   bisync daemon              │
│                                              │
│  fanotify                                    │
│  watcher ──► debouncer ──► changelog (SQLite)│
│                                    │         │
│                             reconciler       │
│                            /         \       │
│                     gRPC client    rsync/SSH  │
│                         │                    │
│                  gRPC server ◄── peer daemon  │
└─────────────────────────────────────────────┘
```

### Watcher

The watcher uses the Linux `fanotify` API with `FAN_MARK_FILESYSTEM` to receive events for an entire filesystem. This is necessary because `FAN_MARK_MOUNT` does not support `FAN_CREATE`, `FAN_DELETE`, or `FAN_MOVED_*` events. Events are reported with `FAN_REPORT_DIR_FID | FAN_REPORT_NAME`, which provides the directory file handle and the filename in each event; the directory path is resolved by calling `OpenByHandleAt` followed by a readlink through `/proc/self/fd/`.

Events are classified into five types: `create`, `modify`, `delete`, `attrib`, and `rename`. Because fanotify does not provide a cookie to correlate `FAN_MOVED_FROM` and `FAN_MOVED_TO` pairs, move operations are treated as a delete of the old path and a create of the new path. This is conservative but correct.

After classification, events pass through a per-sync-pair debouncer. The debouncer holds events for a configurable duration (default 5 s) and collapses repeated events for the same path into the latest one, reducing unnecessary transfers when editors save many intermediate states.

The watcher also suppresses events generated by its own rsync processes. It does this by checking `/proc/{pid}/comm` for the string `rsync`, which catches both outgoing transfers and incoming rsync sessions from the peer. Without this filter, an incoming rsync write would generate a changelog entry on the receiver, which would then loop back to the sender.

### Changelog

Each debounced event is written to a SQLite database as a changelog entry. The schema is:

```sql
changelog (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    sync_pair     TEXT    NOT NULL,
    path          TEXT    NOT NULL,
    event_type    TEXT    NOT NULL,   -- create | modify | delete | attrib | rename
    rename_to     TEXT,               -- populated for rename events
    file_size     INTEGER,
    file_mtime    INTEGER,
    file_mode     INTEGER,
    is_dir        INTEGER NOT NULL DEFAULT 0,
    hlc_timestamp TEXT    NOT NULL,
    node_name     TEXT    NOT NULL,
    synced        INTEGER NOT NULL DEFAULT 0,
    peer_ack      INTEGER NOT NULL DEFAULT 0,
    created_at    TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
)
```

Entries are timestamped with a Hybrid Logical Clock (HLC) rather than wall time. An HLC combines a physical timestamp with a logical counter, so entries remain causally ordered even when the two nodes have slightly different clocks. The format is `{RFC3339Nano}:{8-digit hex counter}`, for example `2026-04-26T12:34:56.789012345Z:00000001`.

WAL mode is enabled by default. Writes are serialised through a single database connection to avoid SQLite write contention.

### Reconciler

The reconciler runs when the watcher signals new entries and also on a 30-second ticker as a fallback. It executes one cycle at a time; if a cycle is already in progress it skips the trigger.

A reconcile cycle proceeds as follows:

1. Call `ExchangeChangelog` on the peer's gRPC server to fetch its unsynced entries.
2. Read local unsynced entries from the changelog.
3. For each unique (sync pair, path) key, compare the local and remote entry:
   - Local only: push the file to the peer via rsync.
   - Remote only: the remote entry represents a change the peer has already pushed. Acknowledge it so the peer knows it was received.
   - Both sides changed: resolve the conflict (see below).
4. Mark local entries as synced in the changelog.
5. Call `AckTransfer` on the peer to mark remote entries as peer-ack'd.

For delete events, the reconciler calls `DeleteFile` on the peer's gRPC server instead of invoking rsync. For rename events, it calls `RenameFile`. These operations are atomic from the peer's perspective.

When a file is missing locally at the time of transfer (deleted after the event was recorded but before rsync ran), the reconciler logs a warning and skips the transfer. A subsequent delete entry will clean up the peer side.

### Conflict resolution

A conflict occurs when both nodes have unsynced entries for the same path. Four policies are available:

`lww` (last-write-wins, the default) compares HLC timestamps and keeps the entry with the higher timestamp. Because each node's HLC advances monotonically and the reconciler merges remote HLC values upon receipt, this produces a consistent ordering even across clock skew.

`alpha_wins` always keeps the entry from the node whose name sorts lexicographically first. This is deterministic and requires no timestamp comparison.

`keep_both` applies last-write-wins to determine a winner, but renames the losing file into a conflict directory (`.bisync-conflicts` by default) before applying the winner. The conflict filename includes the node name and a timestamp.

`manual` blocks synchronisation for the conflicting path until a human intervenes. The path remains blocked until the file is deleted on at least one side.

In all policies, a modify or create event beats a concurrent delete, preserving data by default.

### Transfer

File transfers use rsync over SSH. The reconciler calls `transfer.Manager.Send` with a list of relative paths; the manager writes a temp file list and invokes rsync with `--files-from`. Up to `transfer.max_concurrent` rsync processes run in parallel.

The rsync command is built with `-avz --dirs --partial --partial-dir=.bisync-partial`. The `--dirs` flag is required for empty directory creation. Partial transfers accumulate in `.bisync-partial` and are resumed on retry. Retries use exponential backoff starting at 10 seconds, capped at 5 minutes, up to 10 attempts.

The SSH command is constructed as:

```
ssh -p {port} -i {key} -o StrictHostKeyChecking=accept-new
```

### gRPC control plane

Each daemon runs a gRPC server on port 50051 (configurable). The server exposes five RPCs:

- `ExchangeChangelog` — returns unsynced entries to the requesting peer, optionally filtered by sync pair and a since-HLC cursor.
- `AckTransfer` — marks entries as peer-ack'd.
- `DeleteFile` — deletes a file, rejecting the request if there are local unsynced changes for that path.
- `RenameFile` — renames a file, rejecting if the destination already exists.
- `Ping` — returns the node name and a status string.

The gRPC server uses no TLS; it relies on the network being trusted (e.g. Tailscale).

### Recovery

When the daemon shuts down gracefully, it writes the current timestamp to the `last_shutdown` key in the changelog metadata table. On the next start, the recovery manager walks each sync pair directory and records a `modify` entry for every file whose mtime is newer than `last_shutdown`. This catches changes that occurred while the daemon was not running.

On first boot (no `last_shutdown` record), the recovery scan is skipped and a warning is logged. Files already present on both nodes at first boot are assumed to be in sync; if they are not, run an initial rsync manually before starting bisync.

### Maintenance

A scheduled goroutine runs daily to prune old changelog entries. Synced entries older than `changelog.retention_days` (default 90) are deleted. Tombstone entries (deletes) are retained for `conflict.tombstone_retention_days` (default 30) to prevent deleted files from being re-created by a peer that hasn't yet reconciled.

## Timing and eventual consistency

The path from a filesystem write to full propagation takes:

- Up to `watcher.debounce_seconds` (default 5 s) for the debouncer to flush.
- A reconcile cycle triggers immediately after debounce, or within 30 s if the trigger is missed.
- rsync itself adds network transfer time.

Under normal conditions changes propagate in well under a minute. The system is eventually consistent: it guarantees that both nodes will converge given sufficient time and connectivity, but not that they are always identical.
